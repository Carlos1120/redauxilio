## Decisiones de implementación

- El correo se normaliza a minúsculas y funciona como nombre de cuenta; el nombre para mostrar es opcional a efectos de autenticación.
- Spring Security gestiona el formulario, CSRF, la protección contra fijación de sesión, los encabezados de seguridad y la cookie HttpOnly/SameSite=Lax.
- Antes de enviar login, registro o logout, `identity-forms.js` pide `/csrf` con `no-store` y actualiza el campo oculto; si no obtiene un token reciente, cancela el envío. La copia offline de `/` elimina los tokens y el service worker usa caché v7 para retirar copias anteriores.
- BCrypt con sal aleatoria y factor de trabajo 12 almacena contraseñas; el valor original no se guarda ni se registra.
- H2 en archivo bajo `data/` permite desarrollo local con persistencia. El perfil `prod` usa PostgreSQL a través de `DB_URL`, `DB_USERNAME` y `DB_PASSWORD`; la cookie segura requiere HTTPS y `SESSION_COOKIE_SECURE=true`.
- El perfil `prod` fuerza HTTPS con Spring Security y procesa `X-Forwarded-Proto` detrás del proxy configurado. El proxy de despliegue debe sobrescribir encabezados reenviados no confiables; desarrollo local mantiene HTTP.
- Cada respuesta lleva `X-Correlation-ID`: se valida UUID entrante o se genera uno. El filtro lo añade al MDC de logs y registra errores 5xx sin añadir trazas a la respuesta pública.
- Todas las rutas no declaradas públicas requieren autenticación. `/api/publications/**` y recursos de consulta permanecen públicos.
- Una cuenta bloqueada recibe el mismo mensaje genérico de acceso fallido que una cuenta con credenciales incorrectas.
- El acceso, registro y cuenta se muestran en un diálogo sobre la consulta del mapa; cambiar entre formularios y volver de una acción conserva la página principal.
