# RA-10 · Avistamientos

## Alcance funcional

Un avistamiento es una observación ciudadana vinculada a un caso público de persona desaparecida; no es una categoría independiente. Registra fecha y hora observadas, sector público, coordenadas aproximadas, descripción y hasta tres fotografías opcionales. La consulta se incorpora al detalle e historial del caso. El registro nunca cambia automáticamente el estado del caso.

La autoría se conserva en SQL para trazabilidad, pero el historial público no expone cuenta, correo ni nombre del autor. Las coordenadas se redondean a tres decimales y los textos reutilizan la detección de datos privados de RA-09. Las consultas e imágenes responden `no-store` y permanecen fuera del caché del service worker.

## Reglas de este incremento

- Solo una publicación visible de categoría `MISSING_PERSON` admite historial público.
- Para añadir observaciones se requiere sesión ciudadana y CSRF.
- Por seguridad, solo se admiten nuevos registros mientras el caso esté `DESAPARECIDA` y no cerrado. La fuente original no especifica qué hacer con casos encontrados/cerrados: Carlos autorizó conservar provisionalmente esta restricción durante las correcciones.
- Fecha futura, coordenadas no finitas/fuera de rango, texto vacío/excesivo o con datos sensibles se rechazan.
- Imágenes opcionales reutilizan validación, decodificación y límites de RA-12; máximo tres de 5 MiB cada una.
- El alta de observación e imágenes es transaccional. Ninguna operación actualiza `operational_status`, `closed` ni `updated_at` del caso.

## Verificación y límites

`MissingPersonSightingTests` acepta H2 en memoria por defecto o una base PostgreSQL aislada mediante `RA10_TEST_DB_URL`, `RA10_TEST_DB_USERNAME` y `RA10_TEST_DB_PASSWORD`. La clase valida el destino antes del arranque: solo acepta PostgreSQL en `127.0.0.1`, base `ra10_test_<12 caracteres hexadecimales>` y usuario `ra10_test`; H2 en memoria es el valor predeterminado. Elimina únicamente IDs/cuentas creados por cada prueba, al finalizar. Las inyecciones de fallo mediante restricciones temporales solo se ejecutan después de esa barrera, en un clúster nuevo y desechable. En PowerShell, exporta esas tres variables y ejecuta `.\mvnw.cmd -B '-Dtest=MissingPersonSightingTests' test`. La ejecución real con PostgreSQL 18.3 pasó 4/4 y cubrió alta HTTP multipart, lectura pública/foto, privacidad, CSRF, rechazo de estados inválidos y rollback de la observación si falla el guardado de la foto.

Maven verify, Node y formato se ejecutan antes de actualizar el PR; el CI se vuelve a comprobar para el HEAD publicado. Revisión visual y aprobación formal de Carlos siguen pendientes. Los detalles reproducibles están en `EVIDENCIAS.md` y el PR.

## Correcciones de revisión cruzada

- Cuota: máximo cinco avistamientos aceptados por cuenta en una hora móvil, compartida entre casos y contando también los ocultos. Se alinea con el límite de altas del MVP para acotar abuso y fotografías; no implica verificación de identidad. El servidor bloquea la fila de cuenta, cuenta registros persistidos posteriores a `ahora - 1 hora` y rechaza con 429 sin insertarlos. Al cumplirse exactamente una hora se libera la cuota. Las operaciones fallidas no consumen cupo.
- Moderación mínima: operador persistente de RA-08, POST `/api/operator/sightings/{id}/hide`, motivo obligatorio de 1–500 caracteres. Oculta solo el anexo y su acceso fotográfico directo, sin cambiar el caso. Original y fotografías permanecen en SQL; un evento privado conserva actor, fecha, motivo y transición visible→oculto. Repetir devuelve 409 sin duplicar auditoría; cualquier fallo de auditoría revierte el ocultamiento. Consulta privada `/api/operator/sightings/{id}/history`. Formulario por ID en `/operator`; sin nuevos roles ni restauración dentro de esta corrección.
- Historial público: `limit` 1–20 (por defecto 20), `offset` no negativo, orden `observed_at DESC, id DESC`; solo visibles. La UI permite cargar más y muestra ID para identificar el anexo a moderar. Cada consulta carga fotos únicamente de esa página. La paginación por offset garantiza continuidad con datos estables; no ofrece una instantánea frente a altas u ocultamientos concurrentes, por lo que debe refrescarse en ese caso.
- El shell PWA avanza a v26 para distribuir la UI actualizada. Historial, imágenes y operaciones privadas mantienen `no-store` y exclusión de caché. No se declara aceptación humana ni integración.
